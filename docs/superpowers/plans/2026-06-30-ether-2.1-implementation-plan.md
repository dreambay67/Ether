# Ether 2.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Ether 2.1 as a robust correction release that fixes panel resizing, inspector readability, connection-role interaction, generation capability controls, node visual differentiation, DreamBay-aligned note shapes, real free drawing, and the test gaps that allowed 2.01 to ship incomplete.

**Architecture:** Replace cosmetic UI patches with durable state models: a shell pane layout controller, a semantic connection-role system with collapsed physical handles, structured provider model profiles, note visual data with reusable stroke drawing, and screenshot-backed acceptance tests.

**Tech Stack:** Electron, React, TypeScript, Vite, @xyflow/react, SQLite, pnpm workspaces, Vitest, Playwright, Codex CLI provider workers, optional API provider infrastructure, DreamBay/Ether brand tokens.

---

## 0. Operating Rules For This Build

- [ ] Do not implement 2.1 as scattered CSS tweaks. Each failing area gets a state model, command path, and tests.
- [ ] Keep CLI Codex as the default provider. Optional API infrastructure may exist but cannot silently execute.
- [ ] Preserve existing dirty user/worktree changes. Do not revert unrelated files.
- [ ] Keep old graphs loadable. Add decoration/migration for legacy handles and edge data.
- [ ] Use DreamBay/Ether tokens from `packages/brand/src/tokens.ts` and `packages/brand/src/brand.css`.
- [ ] Validate with unit tests, renderer smoke tests, and screenshots before calling the build complete.
- [ ] Use subagents only on disjoint write sets. The integration owner resolves shared model changes.

## 10. Implementation Order

Recommended order:

1. Phase 0 baseline tests.
2. Phase 1 layout and inspector.
3. Phase 2 connection architecture.
4. Phase 3 provider profiles.
5. Phase 5 note visuals and drawing.
6. Phase 4 reference upgrade.
7. Phase 6 help and polish.
8. Phase 7 integration and verification.

Reasoning:

- Layout gives every other UI test a stable frame.
- Connection architecture is the riskiest change and should land before small connection polish.
- Provider profiles touch engine, providers, inspector, and metadata, so they should land before final run tests.
- Notes and references can progress in parallel after the connection model settles.

## 11. Risk Register

- [ ] **Risk:** React Flow connection lifecycle cannot support the exact wheel-before-release workflow cleanly.
  **Mitigation:** Use local connection draft state plus document-level wheel/key listeners during active drag.

- [ ] **Risk:** Collapsed handles break old graph edges.
  **Mitigation:** Add legacy decoration and migration tests before deleting old handle assumptions.

- [ ] **Risk:** Codex CLI does not expose direct model capability metadata.
  **Mitigation:** Return static adapter profiles with clear source labels and record actual output dimensions.

- [ ] **Risk:** Free Draw conflicts with React Flow drag/pan behavior.
  **Mitigation:** Stop propagation while drawing and provide explicit draw/edit mode for Free Draw nodes.

- [ ] **Risk:** Subagents conflict in shared CSS.
  **Mitigation:** Assign CSS sections by component, then integration owner reconciles tokens and responsive rules.

- [ ] **Risk:** More tests become flaky because Electron layout timing is asynchronous.
  **Mitigation:** Use stable test ids, wait for bounding boxes, and assert geometry after animation-free state.
