## 1. Mandate

Reopen the rejected Ether 4.0 release candidate and complete its authoring product without discarding the sound 4.0 backend. The work must repair the blank-canvas experience first, then prove all retained backend capabilities through actual user workflows.

The fixer task implements and validates. It does not green-light release, merge to `main`, tag, publish a GitHub Release, or call the product complete. It reports an exact candidate commit to the original review task, which independently operates the installed application and makes the release recommendation.

## 2. Non-Negotiable Process Corrections

1. The acceptance ledger, not task checkboxes or test totals, determines completion.
2. Every visible workflow task includes an installed-app acceptance step in the same phase.
3. No deletion of an existing user-facing capability occurs without a written parity/conversion table and passing replacement journey.
4. No primary journey uses a pre-seeded graph to prove creation or editing.
5. A reviewer starts with the application behavior, then reads implementation details.
6. Implementer and reviewer cannot both infer success from the same mocked bridge.
7. A phase cannot close while one of its assigned requirements is `OPEN`, `FAIL`, `MISSING`, `BLOCKED`, or `PRESENT-UNPROVEN`.
8. A historical green check is rerun when recovery code can affect its evidence.
9. The worker reports blockers honestly and continues independent work; it never edits the claim to fit the result.
10. The product owner alone supplies `OWNER-ACCEPTED` evidence.

- Every prompt names owned files, acceptance IDs, non-goals, required tests, and expected handoff.

- The main worker reviews every diff before integration.
- High-risk tasks receive a different-model reviewer.
- Reviewer findings are resolved before a phase gate; reviewers do not edit unless explicitly reassigned.
- The main worker maintains `docs/evidence/ether-4.0-recovery/subagent-ledger.md` with model, effort, task, commit, findings, and disposition.
