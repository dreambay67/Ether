# Ether 4.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementation task receives an implementer, a specification reviewer, and a code-quality reviewer before its phase gate is closed.

**Goal:** Deliver a professional Windows Ether 4.0 application built around one portable `.ether` document, intelligent Codex LLM Workers, real Codex and Antigravity image providers, durable multimodal workflows, executable recipes, and a deeply integrated Codex plugin.

**Architecture:** Renew the current Electron/React/React Flow monorepo in place while replacing the 2.5 directory-project and monolithic engine contracts. Introduce pure schema, single-file document, graph-kernel, intelligence, execution, recipe, and application-service packages; make desktop, MCP, and the Codex plugin typed clients of the application service.

**Tech Stack:** TypeScript 5.8+, Zod, Node built-in SQLite, Electron 36+, React 19, React Flow 12, Vite 6, Vitest 3, Playwright, MCP TypeScript SDK, Codex App Server/CLI, Antigravity CLI, electron-builder/NSIS, pnpm workspaces.

## 1. Execution Protocol

### 1.1 Approval And Change Control

- No implementation phase starts until the three normative Ether 4.0 documents are approved.
- A changed product decision first updates the design and technical specifications, then the affected plan tasks.
- No legacy importer, directory-project compatibility layer, browser automation, hidden API fallback, or placeholder provider may be introduced.
- The optional Live Output Folder remains disabled by default.

### 1.2 Subagent Workflow

For each task:

1. Main agent publishes the task’s exact file ownership and current base revision.
2. A fresh local implementer subagent writes only the assigned files and tests.
3. Main agent runs the narrow tests and reviews the diff.
4. A specification reviewer checks behavior against the normative documents.
5. A code-quality reviewer checks boundaries, safety, tests, and maintainability.
6. Implementer addresses findings; main agent reruns narrow tests.
7. Main agent stages only the paths declared under that task’s **Files** list, inspects `git diff --cached`, scans the staged index for secrets/generated artifacts, records completion, and creates the planned local commit. Broad staging is forbidden once the checkpoint is made.

Parallel workers are allowed only for disjoint write sets. Document/schema changes that affect several packages remain on the main critical path.

### 1.3 Phase Gates

No phase begins until the previous phase’s gate passes. A gate requires:

- Phase-focused unit/integration tests green
- Package typechecks green
- Diff review and secret scan clean
- Normative acceptance items for the phase demonstrated
- No new misleading controls, `TODO` production paths, or skipped core tests

### 1.4 Git Policy

- Preserve the current dirty 2.5 worktree through an intentional checkpoint before refactoring.
- Work on `feature/ether-4.0`.
- Use focused commits listed in this plan; never force-push.
- Final publication target is `https://github.com/dreambay67/Ether.git`.
- The GitHub push is the final task after packaged acceptance, documentation, and privacy/secret audit.

## Task 14: Complete Execution And The Application-Service Contract

### Contract freeze

- The public application boundary is `execute(command)`, `query(query)`, and `subscribe(listener)`. Every mutation is command-ID-idempotent, every failure uses `EtherError`, and every command, query, response, and event is validated by the shared schema package.
- Output versions remain immutable. `output.edit` and `output.restore` create manual descendants; `output.pin` changes an edge selector atomically through a graph transaction. Review supports approve, reject, rate, tag, route, and completion of a durable human Compare checkpoint.
